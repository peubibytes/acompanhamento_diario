1Visão geral

O que a aplicação resolve, os conceitos do domínio e o que está dentro e fora do escopo.

1.1 Propósito

O Acompanhamento Diário substitui uma planilha Excel de controle de horas por uma aplicação web. O usuário registra, ao longo da semana, as atividades realizadas, com horário de início e fim. A aplicação consolida esses registros em métricas diárias e semanais e indica, a cada momento, quanto da carga horária do ciclo já foi apontada.

O objetivo operacional é chegar à quinta-feira com 100% das horas preenchidas. Nesse dia, o usuário transfere os apontamentos para um sistema externo (Azure DevOps). Essa integração está fora do escopo da versão atual.

1.2 Conceitos do domínio

TermoDefinição
CicloPeríodo de apuração que começa na sexta-feira e termina na quinta-feira seguinte. Contém 5 dias úteis: Sex, Seg, Ter, Qua e Qui.

2Regras de negócio

Todas as regras ficam no pacote shared e são consumidas igualmente pelo servidor e pela interface.

2.1 Ciclo sexta → quinta

O ciclo de qualquer data é derivado dela mesma, sem tabela de semanas. A data de início é a sexta-feira mais recente que seja menor ou igual à data de referência:

offset = (diaDaSemana(data) − 5 + 7) mod 7      // 0 = domingo … 6 = sábado; 5 = sexta
inicio = data − offset dias                      // sexta-feira
fim    = inicio + 6 dias                         // quinta-feira
diasUteis = inicio + [0, 3, 4, 5, 6]             // Sex, Seg, Ter, Qua, Qui

Sábado e domingo pertencem ao ciclo da sexta-feira anterior, mas não são dias úteis e não aceitam lançamentos. As datas trafegam como texto ISO AAAA-MM-DD, e a aritmética é feita em UTC para evitar desvios de fuso horário e de horário de verão.

2.2 Meta diária

  • Opções: 5h30 (330 min), 8h48 (528 min) ou “Outro”, informado em hh:mm entre 1 min e 24h.
  • Versionamento por ciclo: cada ciclo guarda a sua meta (cycle_goals). Sem registro próprio, o ciclo usa a meta padrão (settings.default_daily_goal_minutes, inicialmente 330).
  • Alteração no ciclo atual ou futuro: a nova meta vale para o ciclo e passa a ser o padrão dos próximos. Antes da troca, os ciclos anteriores que tinham atividades e ainda seguiam o padrão antigo têm a meta congelada, para que o histórico não seja recalculado.
  • Alteração em ciclo passado: afeta somente aquele ciclo.

A duração não é persistida: é sempre calculada como endMinute − startMinute. Horários sobrepostos no mesmo dia são aceitos, mas geram avisos (warnings) na resposta da API.

2.5 Métricas do ciclo

MétricaRegra
Meta semanalg × 5
Total realizadoΣ minutos dos 5 dias úteis
Dias conformesquantidade de dias com conforme, exibida como X/5
Dias excedidosquantidade de dias irregulares
% preenchidofloor(total × 100 ÷ metaSemanal). O arredondamento para baixo garante que 100% só apareça com a semana realmente completa.
Situação geral“100% conforme / Meta total atingida” se os 5 dias forem conformes; senão “X/5 conformes / Ajustes pendentes”
Regra de conformidade estrita. Somente o valor exato da meta é conforme. Excesso não compensa falta: um ciclo com 100% de horas distribuídas de forma desigual continua irregular. A interface só sinaliza “pronto para apontar” quando os 5 dias estão conformes.

3Arquitetura

Monorepo com três pacotes npm (workspaces), um servidor HTTP único e banco SQLite em arquivo.

3.1 Fluxo de uma requisição

  1. A tela chama um hook do TanStack Query (ex.: useCycle(data)), que executa fetch('/api/cycles/:data').
  2. O Express valida os parâmetros com Zod e consulta o repositório, que executa SQL preparado no SQLite.
  3. As atividades do ciclo são agregadas por buildCycleSummary (pacote shared) e devolvidas como JSON.
  4. Mutações (criar, editar, excluir, alterar meta) invalidam as consultas cycle e activities; a interface é atualizada automaticamente.

3.2 Decisões técnicas

DecisãoMotivação
Tempo em minutos inteirosComparações exatas (330 === 330). Elimina o arredondamento ROUND(x·1440) que a planilha usava para contornar ponto flutuante.
Domínio no pacote sharedUma única implementação das regras para servidor e interface, testável sem I/O.
node:sqliteDriver SQLite embutido no Node.js: sem dependência nativa para compilar (relevante no Windows) e com API síncrona simples.
TypeScript sem build no servidorO Node executa .ts diretamente (type stripping). O código segue erasableSyntaxOnly: sem enum, namespace ou parameter properties.
Duração derivadaPersistir apenas início e fim evita inconsistência entre colunas.
Ciclo derivado da dataDispensa tabela de semanas e qualquer rotina de “abertura” de ciclo.
Estado na URLA data de referência (?data=) sobrevive a recarregamentos e permite compartilhar links para um dia específico.

5Back-end

Servidor Express organizado em quatro módulos: conexão, repositório, aplicação HTTP e ponto de entrada.

5.1 db.ts — esquema

Abre o banco, ativa o modo WAL e aplica o esquema de forma idempotente (CREATE … IF NOT EXISTS). Restrições de integridade também são impostas pelo SQLite (CHECK).

CREATE TABLE activities (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  date         TEXT    NOT NULL,                 -- 'AAAA-MM-DD'
  start_minute INTEGER NOT NULL,
  end_minute   INTEGER NOT NULL,
  project      TEXT    NOT NULL,
  description  TEXT    NOT NULL DEFAULT '',
  notes        TEXT    NOT NULL DEFAULT '',
  status       TEXT    NOT NULL CHECK (status IN
               ('concluido','nao_concluido','pendente_aprovacao','nao_iniciado')),
  created_at   TEXT    NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at   TEXT    NOT NULL DEFAULT CURRENT_TIMESTAMP,
  CHECK (end_minute > start_minute)
);
CREATE INDEX idx_activities_date ON activities(date);

CREATE TABLE cycle_goals (cycle_start TEXT PRIMARY KEY, daily_goal_minutes INTEGER NOT NULL);
CREATE TABLE settings    (key TEXT PRIMARY KEY, value TEXT NOT NULL);

5.2 repo.ts — repositório

Encapsula todo o SQL em prepared statements e converte as linhas (snake_case) para objetos do domínio (camelCase).

OperaçãoDescrição
listActivities(from, to)Atividades no intervalo, ordenadas por data, início e id.
getActivity · createActivity · updateActivity · deleteActivityCRUD por id. A atualização também grava updated_at.
findOverlaps(a, ignoreId)Atividades do mesmo dia com start < a.end e end > a.start. Intervalos que apenas se encostam não contam como sobreposição.
goalForCycle(cycleStart)Meta do ciclo ou, na ausência, a meta padrão.
setCycleGoal(start, min, makeDefault)Grava a meta em transação. Com makeDefault: congela os ciclos anteriores, remove metas de ciclos posteriores e atualiza o padrão.

5.3 app.ts — aplicação HTTP

  • createApp({ repo, today?, staticDir? }) cria a instância Express. today é injetável para testes determinísticos.
  • Corpos e parâmetros são validados com Zod. A primeira mensagem de erro é devolvida em error, e a lista completa em issues.
  • JSON malformado gera 400, rotas /api inexistentes geram 404 e exceções não tratadas geram 500 com registro no console.
  • Quando web/dist existe, o servidor serve os arquivos estáticos e devolve index.html para as demais rotas (SPA fallback).

7.4 Linguagem visual e tema

  • Tokens de design em variáveis CSS (index.css), expostos ao Tailwind via @theme inline (ex.: bg-surface, text-ink-2).
  • Cores de status reservadas: verde (conforme), âmbar (abaixo da meta), vermelho (acima da meta/irregular) e cinza (pendente). Toda cor de status vem acompanhada de ícone e rótulo, nunca sozinha.
  • Tema: segue prefers-color-scheme até o usuário escolher um. O ThemeToggle grava data-theme em <html> e persiste a escolha em localStorage['tema']. Um script inline em index.html aplica o tema salvo antes da primeira pintura, evitando o efeito de piscar.
  • Acessibilidade: rótulos ARIA nos controles de ícone, role="tablist" nas abas de dias, foco visível e respeito a prefers-reduced-motion.

8Execução e operação

A aplicação roda localmente, sem serviços externos. O único requisito é o Node.js.

8.1 Requisitos

  • Node.js ≥ 23.6, necessário para executar TypeScript nativamente e para o módulo node:sqlite. O projeto foi desenvolvido no Node 26.
  • npm 10 ou superior.

8.2 Instalação e uso

git clone https://github.com/peubibytes/acompanhamento_diario.git
cd acompanhamento_diario
npm install

npm run dev      # desenvolvimento: API em :3001 e interface em http://localhost:5173
npm start        # uso diário: build da interface + servidor único em http://localhost:3001

8.4 Dados e backup

Todos os dados ficam em server/data/acompanhamento.db, junto com os arquivos -wal e -shm do modo WAL. O diretório é ignorado pelo git. Para backup, copie o arquivo com o servidor parado. Para mover os dados, use DB_PATH.

Privacidade. O repositório é público. Registros reais de trabalho (o banco local e a planilha de referência) nunca são versionados: server/data/ e *.xlsx estão no .gitignore, e os exemplos de código usam dados fictícios.
